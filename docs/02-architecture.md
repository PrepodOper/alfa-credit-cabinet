# 02 · Архитектура решения

## 1. Обзор

Решение — cloud-native веб-приложение из двух контейнеров:

```
┌─────────────────────────────┐         ┌──────────────────────────────────────┐
│  frontend (React + Vite)    │  /api   │  backend (FastAPI, Python 3.12)      │
│  SPA, nginx в проде         │ ──────► │  REST + JWT, SQLAlchemy              │
└─────────────────────────────┘         │                                      │
                                        │  services/                           │
                                        │   ├─ pipeline.py  (конвейер)         │
                                        │   ├─ scoring.py   (скоринг+решения)  │
                                        │   ├─ registry.py  (моки БКИ/ЕГРЮЛ)   │
                                        │   ├─ workflow.py  (статусы, SLA)     │
                                        │   └─ news.py      (персонализация)   │
                                        │                                      │
                                        │  SQLite (WAL) / PostgreSQL-ready     │
                                        └──────────────────────────────────────┘
```

**Почему так:**

- **FastAPI** — контракт-first (OpenAPI из коробки), Pydantic-валидация на границе, async-готовность,
  широкая распространённость в финтехе и enterprise-разработке.
- **React + Vite** — SPA с мгновенной сборкой, раздача статики через nginx; тот же билд умеет
  раздавать FastAPI (режим одного контейнера для демо).
- **SQLAlchemy 2.x + SQLite в WAL** — единый воспроизводимый запуск на обычном ПК; переключение на
  PostgreSQL через `DATABASE_URL` без изменения кода (используется только стандартный SQL).
- **Docker Compose** — один контейнер бэкенда и один фронтенда, провижининг БД — автоматически при
  старте (create_all + идемпотентный сидинг).

## 2. Компоненты backend

| Модуль | Ответственность |
|---|---|
| `main.py` | Сборка приложения, CORS, подключение роутеров, раздача SPA, старт-ап инициализация |
| `config.py` | Конфигурация из переменных окружения (12-factor) |
| `database.py` | Движок, сессии, PRAGMA для SQLite (WAL, foreign keys, busy timeout) |
| `models.py` | ORM-модель данных: пользователи, компании, продукты, заявки, документы, события, новости |
| `schemas.py` | Контракты API (Pydantic), сериализация ответов |
| `security.py` | PBKDF2-хэширование паролей, JWT, зависимости авторизации и ролей |
| `serializers.py` | ORM → API-контракт, снимки клиента для бэк-офиса |
| `services/pipeline.py` | Оркестрация обработки заявки, формирование предложения/отказа |
| `services/scoring.py` | Балльная модель, риск-классы, affordability, маршрутизация |
| `services/registry.py` | Моки внешних источников (БКИ, ЕГРЮЛ/ЕГРИП, ФНС) |
| `services/workflow.py` | Статусная модель, журнал событий, следующий шаг, SLA |
| `services/news.py` | Подбор и ранжирование ленты, объяснение релевантности |
| `seed.py` | Синтетические данные: 3 компании, 4 продукта, 5 пользователей, 19 новостей |

## 3. Ключевой поток: обработка заявки

```
Клиент                API                 Конвейер              Андеррайтер
  │  POST /applications │                     │                       │
  ├────────────────────►│ создаёт draft       │                       │
  │                     │ → submitted         │                       │
  │                     ├─── background ─────►│ validation            │
  │                     │                     │ обогащение (БКИ/ЕГРЮЛ)│
  │                     │                     │ scoring               │
  │                     │                     │ routing               │
  │                     │                     ├─ A/B ──► offer_issued │
  │                     │                     ├─ C/D ──► manual_review ├─► /bank/tasks
  │                     │                     └─ E/стоп ─► declined    │
  │  GET /applications/{id} (polling 1.8 c)   │                       │
  ├────────────────────►│ статус + события    │                       │
  │                     │                     │◄── decision (4 варианта)
  │                     │                     │ offer_issued/declined │
  │  POST /offer/accept │                     │                       │
  ├────────────────────►│ signing             │                       │
  │  POST /sign         │                     │                       │
  ├────────────────────►│ funded (счёт, дата) │                       │
```

Обработка выполняется фоновой задачей FastAPI (`BackgroundTasks`) в отдельной сессии БД. Клиент
опрашивает карточку заявки (polling), поэтому UI динамически меняет статусы без перезагрузки.
Искусственные паузы между шагами настраиваются `DEMO_DELAY_SCALE` (0 — для тестов).

**Идемпотентность и целостность:** переходы проверяются по текущему статусу (`409`, если переход
недопустим), все изменения статуса идут через один метод `workflow.move`, который одновременно
пишет событие в журнал. Данные клиента и заявки читаются из БД, повторный ввод исключён.

## 4. Разграничение доступа

| Роль | Доступ |
|---|---|
| `client` | Только своя компания и свои заявки (`company_id` из JWT-пользователя) |
| `bank` | Очередь, карточки заявок всех компаний, решения, аналитика |

Реализовано через зависимости `require_role(...)` и проверку `app.company_id == user.company_id`.
Клиентские эндпоинты недоступны банку и наоборот (`403`). Токен — JWT HS256, срок жизни настраивается.

## 5. Enterprise-ориентированность

| Аспект | Как учтено |
|---|---|
| Безопасность | Хэширование паролей PBKDF2-SHA256 (120k итераций), JWT с TTL, ролевая модель, нет секретов в коде (env), CORS настраивается |
| Аудит | Каждое действие (клиент/банк/система) пишется в `application_events` с ролью, именем и временем |
| Наблюдаемость | `/api/health` + Docker HEALTHCHECK, структурные статусы вместо свободного текста |
| Отказоустойчивость | SQLite WAL + busy_timeout, транзакционность на шаг конвейера, защита фоновой задачи от исключений |
| Масштабирование | Stateless API (JWT, без серверных сессий) → горизонтальное масштабирование; вынос конвейера в очередь (Celery/RQ) не меняет контракты |
| Сопровождаемость | Слои: routers → services → models, чистые функции скоринга, типизированные схемы, 13 автотестов |
| Конфигурируемость | Все параметры через env, `.env.example`, отдельные настройки окружений |
| Зависимости | Только open-source, зафиксированные версии в `requirements.txt` и `package-lock.json` |

## 6. Путь к продакшену (эволюция)

1. **БД:** PostgreSQL + миграции Alembic (модель уже совместима).
2. **Конвейер:** вынести обработку в очередь (Celery/RabbitMQ), ввести outbox-паттерн для событий.
3. **Интеграции:** заменить `services/registry.py` на клиентов реальных API с circuit breaker,
   таймаутами, кэшем и трассировкой; секреты — в Vault.
4. **Идентификация:** SSO/OpenID Connect, MFA, раздельные клиентский и банковский контуры.
5. **Наблюдаемость:** OpenTelemetry, метрики Prometheus/Grafana, алерты на SLA и ошибки.
6. **Документы:** S3-совместимое хранилище, антивирус-скан, OCR, интеграция с ЭДО/УКЭП.
7. **Скоринг:** версионирование моделей, мониторинг PSI/ROC, A/B-тесты порогов, объяснимость (SHAP).
8. **Масштаб:** read-replicas для аналитики, кэш ленты (Redis), CDN для статики.
